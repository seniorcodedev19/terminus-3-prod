Hardware/CAD tasks are graded on geometry, and there are several ways to establish it. The approaches below are the ones recommended in this subcategory. Which ones you can use depends on the engine, so check the details under each. They combine, and most tasks need more than one.

What an approach can tell you follows from what it asks. A probe reports whether material exists at one location. A void probe and a solid probe put a boundary somewhere between them. That is an interval as wide as the gap between the probes, not a measured value. If your measurement points are spaced farther apart than your required tolerance, you have not verified whether the part is correctly made.

This page covers only what is specific to geometry. The general rules — reject a wrong solution, match instruction tolerances to test tolerances, don't grade a proxy — are in What Makes a Good Task, Writing Tests and the Quality Guidelines, and they apply here too.

Choosing an Approach
Direct measurement	the exact value of a named feature	B-Rep kernels	anything without a parameter to query
Invariant checking	that the shape follows a known formula	any engine, given a formula	everything the formula leaves out
Symmetric difference	total agreement with a rebuilt reference	any engine that can boolean	where the part is wrong
Sampling	material presence at chosen points	any engine	any dimension it does not bracket
Functional verification	that the part does its job	any engine	errors that do not affect the job
The kernel is the geometry engine under the CAD library, the code that actually stores the shapes. CadQuery, build123d, FreeCAD and pythonOCC are front ends on one kernel, OpenCASCADE. It stores a cylinder as "radius 13, on this axis", so you can ask for the radius and get it back.

OpenSCAD and Blender store that same cylinder as a few hundred triangles. There is no radius anywhere in that, so direct measurement is not available on them at all.

Most tasks need two approaches. The pairings that work are noted under each.

Getting the toolchain into your image. No CAD toolchain is on the canonical base image list, so a CAD task normally either uses a non-canonical base that already carries one, or installs it onto a canonical distro base. Both are allowed — a non-canonical base passes as long as the reason is written as a comment in the Dockerfile. See Using a non-canonical base image.

Check which version you end up with, particularly for a parametric task. A distro package may be several years behind the current release, and older builds carry the topological-naming behavior described under Recompute What You Require — a correct submission can fail on rebuild through no fault of its own.

1. Direct Measurement
Ask the solid for a feature and compare its parameter against the specified value.

python

Copy
# Every B-Rep kernel exposes faces, their surface type and their parameters;
# the spelling differs by engine, the technique does not.
# Select by role, not by global orientation or by position in the face list.
bores = [f for f in faces_of(solid) if is_cylindrical(f) and is_internal(f)]
assert len(bores) == 1, f"expected one bore, found {len(bores)}"
assert abs(radius_of(bores[0]) * 2 - 26.0) <= 0.05
Everything else tells you the part is close enough. This tells you the bore is 26.03 mm.

2. Invariant Checking
Instead of measuring a dimension, check a formula that is true of the correct shape and false of everything else.

python

Copy
# points sampled along one tooth flank, in the part's own frame:
# the gear axis fixes the center, not the global origin
flank = to_polar(sample(tooth_flank), axis=axis_of(bore))
# On a single flank, theta - inv(acos(rb/r)) is the same constant at every point
# (the sign follows the flank's handedness). The constant absorbs any rotation
# about the axis, so only its spread carries information.
consts = [theta - inv(acos(rb / r)) for r, theta in flank if r > rb]
assert (max(consts) - min(consts)) * rb <= SCATTER_TOL   # spread as arc length
The formula has to hold everywhere along the curve. An arc drawn between the same two endpoints passes a check on those endpoints and fails this one.

Other formulas worth knowing. Unrolling a curved sheet does not stretch it, so an arc keeps its length in the flat pattern. A helix has constant pitch. A surface of revolution has the same radius all the way round at a given height.

3. Symmetric Difference
Build the expected solid from the specification and boolean-difference it against the submission in both directions.

python

Copy
reference = build_expected(spec)              # derived from the spec, never stored
aligned   = align_to(submitted, reference)    # required wherever pose is free
lost  = volume_of(cut(reference, aligned))    # material missing
extra = volume_of(cut(aligned, reference))    # material that should not be there
assert lost + extra < 1e-5
What is left over after both cuts is everything that differs, including the features you forgot to list.

4. Sampling
Ask whether material exists at chosen points.

python

Copy
# ❌ This looks like it tests the slot width. It does not.
assert not inside(x=42, y=28, z=4)     # void at the slot center
assert inside(x=42, y=34, z=4)         # solid 6 mm away
Those two assertions check far less than they look like they check. The slot is centered at y = 28. The first says there is no material at the center, so the width is more than 0. The second says there is material 6 mm out, so the half-width is under 6 and the width is under 12. A slot of any width between 0 and 12 mm passes. The instruction said 9 mm.

A probe puts bounds on a dimension. It never measures one. No tolerance constant fixes that. The check has to change kind:

python

Copy
# ✅ Measure the feature off the solid
width = measure_void_extent(solid, along="y", through=(42, 28, 4))
assert abs(width - 9.0) <= 0.5, f"slot is {width:.4f} mm wide, expected 9.0"
Where a bracket is the only option, make the pair tight enough to count as a measurement. The bounds are only as tight as the gap between the probes.

python

Copy
# ✅ Probes 0.4 mm apart bracket the same slot to ±0.4 mm
assert not inside(42, 32.3, 4)     # void  -> width >= 8.6
assert     inside(42, 32.7, 4)     # solid -> width <  9.4
⚠️ Sampling measures a dimension only when it is finer than the tolerance. If the gap between the "inside" and "outside" probes exceeds the tolerance you would use for a direct measurement, the pair does not test the dimension.

Two probes put the edge somewhere between them. That is as close as probing gets.

The same limit applies whenever a test computes a number by sampling the shape rather than probing it: discretizing a curve to measure a length, tessellating a surface to get an area or volume. The sampling error lands inside the number the tolerance is applied to, so part of the band is spent before the part's own error counts. A 0.25 mm bound measured against an outline whose sample spacing is 0.23–0.28 mm leaves a submission almost no room, whatever the constant says. Compute the spacing and compare it to your tolerance. Record both in verification_explanation.

Coarseness also flattens differences. Recovering cell occupancy at a 15 mm pitch will call two plates identical when they differ only in sub-millimeter socket detail, so guard any duplicate or equality claim with a volume check.

5. Functional Verification
Run the part and check that it does its job.

python

Copy
# Ride a roller of the stated radius around the profile through a full
# revolution and recover the lift the cam actually produces.
lift = ride_follower(section, roller_radius, steps=720)
assert abs(lift - programmed_lift) <= LIFT_TOL
assert contact_maintained, "the roller lost contact with the profile"
A cam profile within tolerance at every point can still produce the wrong lift. Running it shows that.

Coverage: Every Stated Dimension Needs a Check
Count the dimensions your instruction states, then count the ones your verifier measures. If the instruction specifies 12 dimensions and the tests measure 3, the task is not verified. It is sampled.

The pattern to avoid is a strict tolerance on the bounding box and nothing comparable on anything inside it:

Overall length / width / height	bounding box	±0.8 mm
Internal bore diameter	one void probe	unbounded
Slot width	two probes 6 mm apart	−9 / +3 mm
Boss diameter	boundary probes	−16 / +8 mm
That verifier has two standards. Hold internal features to the same one as the envelope.

Checks That Are Routinely Forgotten
Through-features. A probe at mid-thickness cannot tell a through-hole from a blind pocket. Probe at both faces, or measure how far the void runs.
Repeated features. If the instruction says "four slots" or "two gussets", check all of them. Probing one and assuming symmetry lets a submission ship with one.
"Exactly N". Confirming N features exist does not stop an N+1th.
Position, not just size. A hole of the right diameter in the wrong place passes a diameter check.
The Volume Floor Is Not a Test
python

Copy
assert volume_of(solid) > 60000     # nominal part is ~118,000 mm³
Half the part can be missing. If you use a volume assertion, compare against a rebuilt expected value with a real tolerance, not a floor. This is Checking a Proxy Instead of the Value from Writing Tests in geometric form.

Your Oracle Can Build the Wrong Part
Correct, Not Just Passing in Writing Oracle Solution applies here with a CAD-specific twist: what has to be checked against the instruction is the solid your oracle produced, not the constants it declares.

This oracle sets the keyway to 4.0 mm and cuts 6.5 mm:

python

Copy
KEYWAY_DEPTH = 4.0          # matches the spec exactly

# ...and then, elsewhere:
cutter = box(width, KEYWAY_DEPTH + 3.0, height,
             at=(-width/2, bore_radius - 0.5, -3.0))
# Cut starts 0.5 inside the bore and runs KEYWAY_DEPTH + 3.0 deep.
# Actual depth: 6.5 mm. The spec says 4 mm. No test measured it.
Open the solid your oracle produced and measure every dimension you wrote in the instruction. Reading the source is not enough, because that source is exactly what looks correct above.

Recompute What You Require
An instruction that asks for a parametric model is asking for one thing: change a driving value and the part updates. That is behavior, and it is not visible in the saved document.

python

Copy
# ❌ Confirms a property holds 140.0. Says nothing about what drives the part.
assert abs(param(doc, "BaseLength") - 140.0) <= 0.01

# ✅ Drive it, recompute, measure the part again.
set_param(doc, "track_count", 8)
recompute(doc)
assert no_errors(doc)
assert count_tracks(solid_of(doc)) == 8
Reading a parameter back tells you a number is stored. It does not tell you the geometry depends on it, and a model that hardcodes the shape stores the same number.

Recompute is where parametric models actually break, which is why the check is worth writing. Feature references are positional — a fillet is applied to Edge12, not to a named edge. Change a driving parameter, the tree re-runs, and the kernel regenerates the edge list. What was Edge12 may now be a different edge, or may belong to something else entirely. The fillet lands in the wrong place, or errors out. Newer CAD releases mitigate this; older ones do not.

So assert on both halves: that the recompute reports no errors, and that the part changed the way the instruction says it should. A model that silently recomputes to the wrong shape passes the first and fails the second.

Set the parameter to a value the shipped fixtures do not already use. Recomputing to the value it already holds proves nothing.

Calibrate Tolerances in Both Directions
Every task must reject a wrong solution, not just accept a right one. For a dimensioned part, that means demonstrating each tolerance band in two directions:

It rejects the intended wrong answer. Not any wrong answer — the plausible misreading of your own spec. Build it and confirm it fails, by a stated margin.
It accepts correct work built differently. Build the same part another way and confirm it passes, with stated headroom.
Record the margin and the headroom in verification_explanation. A range only the reference implementation can hit is too tight; one that obviously wrong answers clear is too loose.

Make Discrimination Automatic
The strongest pattern seen in this subcategory generates plausible wrong answers at test time and asserts each one genuinely differs from the truth:

python

Copy
@pytest.mark.parametrize(("label", "value", "differs"), WRONG_READINGS)
def test_wrong_answers_are_refused(label, value, differs):
    """A plausible misreading really does differ, so the checks test something."""
    assert differs, f"{label} agrees with the contract, so it tests nothing"
This prevents the worst outcome — passing a candidate for agreeing with an answer your checks were never able to tell apart.

Stating Dimensions
General instruction style is covered in Instruction Prompt Styling. One point is specific to CAD, and it follows from the fact that a CAD instruction is a machining spec — every dimension stated will be built and may be graded.

Do not hedge a dimension you intend to grade. "About 2 mm" and "approximately 4 mm deep" carry grading weight they cannot support. If a test checks it, state it exactly. If it genuinely does not matter, say that instead.

Declare What Is Free, and Test That It Is
A fully dimensioned part has one correct shape but many correct ways to build and store it: different construction order, different curve resolution, different pose, different feature tree. Your verifier has to ignore those differences unless the instruction constrains them. A submission will not know they are free unless you say so, and where something is required, such as a specific orientation or a particular clocking, write it down. It will not be inferred from the geometry.

A verifier that measures a feature from an absolute angle rather than a relative one quietly requires a rotation the instruction never mentions:

python

Copy
# ❌ Depends on how the part happens to be rotated about its own axis
theta = cluster(angles_of_one_flank_family)
span  = rb * ((k - 1) * pitch + 2 * theta)

# ✅ Invariant: difference of the two families cancels the rotation
psi  = ((hot_cluster - cold_cluster) % pitch) / 2
span = rb * ((k - 1) * pitch + 2 * psi)
The first version fails its own oracle if a gear is rotated 1°. The second does not.

Practical test. Take your oracle's own output, change something the instruction does not constrain, and re-run your verifier:

rotate or translate the part
rebuild it with a different feature order
rebuild the curves at coarser and finer resolution
export through a different route
If any of those fail, your verifier is too strict and will reject correct submissions.

Do Not Describe the Feature Tree
Describe the part. Not the steps that build it.

The delivered tree carries the master track as a single swept cut and reaches the full set of tracks through one polar pattern feature of track_count occurrences.

Six identical swept cuts produce the same solid and fail this. The instruction is describing a modeling session, not a part.

The same instruction already says what it wants:

changing ball_dia or track_count has to recompute cleanly with the tracks following

That is testable on the part, and it is what your verifier should assert — see Recompute What You Require. Any model that passes it is parametric however it was built.

Do not write:

which feature type makes each shape — Pad, Pocket, Revolution, Fillet, Chamfer
how many features, or that they be separately named
the order to apply them in
which features are banned — primitives, AdditiveBox, SubtractiveCylinder
Those names are FreeCAD's; every tool has its own, and none of them belong in an instruction. Write the dimensions, and write the behavior you need the model to have.

Measure the Geometry, Not a Report About It
B-Rep engines, which share the OpenCASCADE kernel.

Topology. An edge count is not a hole count. On a cylinder, sphere or torus the seam is owned once by one face, so "edges touching fewer than two faces" fires on every round feature. The shape is closed; the count says otherwise. Use the kernel's own shell-closure test, or exclude seams from the count.

Validity. A shape can report valid and still answer point-containment wrongly. Face merging does this — removeSplitter() keeps the volume correct and isValid() true, while points inside the shape test as outside. Use boolean intersection rather than point sampling to measure occupancy.

Approximation. The mesh is not the solid. Two identical solids built differently tessellate differently, so grading mesh volume grades the tessellation. Use the kernel's exact mass properties.

Pre-Submission Checklist
This is in addition to the general Submission Checklist, not a replacement for it.

 Every dimension stated in the instruction has a test that measures it, by an approach that can see it
 Where sampling is used, the spacing is finer than the tolerance it feeds
 Through-features are verified at both faces, not just mid-thickness
 Every repeated feature is checked, not one representative
 If the instruction asks for a parametric model, a test drives a parameter, recomputes, and measures the result
 The oracle's built geometry has been measured against the instruction, not just its source
 The verifier passes on the oracle's output after a rigid transform / rebuild / re-discretization
 The intended wrong answer has been built and confirmed to fail, with the margin recorded
 Tolerance bands are justified in verification_explanation, including their measurement grain
 Anything the instruction leaves free is stated as free, and no feature tree is prescribed
